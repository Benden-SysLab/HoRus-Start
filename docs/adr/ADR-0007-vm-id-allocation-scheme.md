# ADR-0007: VM ID Partitioning & Deterministic Allocation Scheme

## Status
**Accepted**

## Context
Random VM ID assignment in Proxmox VE clusters creates confusion, makes automation tracking difficult, and increases the risk of ID collision across cluster nodes.

## Decision
We reserve the **`9000–9999` VM ID range** exclusively for read-only infrastructure templates in Proxmox VE, partitioned by distribution and archetype:

| VM ID Range | Distribution / Category | Example |
| :--- | :--- | :--- |
| `9000–9009` | Debian Linux Templates | `9000` (Debian 13 Base), `9001` (Debian 13 Docker) |
| `9010–9019` | Ubuntu Linux Templates | `9010` (Ubuntu 24.04 Base) |
| `9020–9029` | Rocky Linux Templates | `9020` (Rocky 9 Base) |
| `9030–9039` | AlmaLinux Templates | `9030` (AlmaLinux 9 Base) |
| `9050–9059` | LXC Container Templates | `9050` (Debian 13 LXC Base) |
| `9090–9099` | Windows Server Templates | `9090` (Windows Server 2025 Base) |

Active production clones generated by Terraform or Proxmox CLI MUST use VM IDs below `9000` (e.g. `100–8999`).

## Consequences
### Positive
- Clear visual distinction in Proxmox VE UI between active workloads and frozen templates.
- Simplifies Terraform filters and Ansible inventory grouping rules.
